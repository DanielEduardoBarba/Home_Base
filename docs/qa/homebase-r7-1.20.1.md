## New bugs

### HB-R7-01 — Security log does not detect a mutated entry — **High**

- **Steps:** On a throwaway runtime, alter a field (for example `message`) on an existing line in `.runtime/security/2026-11-13.jsonl`, leaving `mac` and `prev` in place. Open Settings → Security, or `GET /api/security/events`.
- **Expected:** The API/UI report a broken chain (`integrityOk=false`) and surface an integrity warning. The mutated line is not treated as a normal event.
- **Actual:** `integrityOk` stayed `true` on both 1.20.0 and 1.20.1. The Security panel listed the altered `TAMPER-R7` text with no warning (`hb-r7-03b-security-filtered.png`). `querySecurityLog` only checks that `mac` / `prev` exist and that the line is valid JSON; it does not recompute the HMAC or verify `prev` against the previous line. `server/test/unit/security_log.test.ts` does not cover detection of an altered entry.

### HB-R7-02 — UI PIN/password security events omit `userAgent` (and path) — **Medium**

- **Steps:** Send a wrong PIN or password with a normal `User-Agent` header. Inspect `/api/security/events` or the CSV export.
- **Expected:** Each event records IP, user agent, device or bot, and source label, as described for the Security page.
- **Actual:** All 14 UI PIN/login events in the throwaway log had `userAgent` missing (and no `path`). MCP events on the same instance did record a user agent. The unknown-source device at `203.0.113.77` also showed `userAgent` as missing.

### HB-R7-03 — Human events from an IP that has MCP presence are labeled Known Grok Bot — **Medium**

- **Steps:** Use a connector (MCP) from `127.0.0.1`, then unlock or fail the PIN from the same address. Open Settings → Security → Devices and the event log.
- **Expected:** Human PIN/login events from loopback stay **LAN** (or the human device class). MCP traffic stays **Known Grok Bot**.
- **Actual:** After an MCP actor is observed on that IP, later human `pin_success` events were stored as `known_grok_bot`. The Devices list showed “LAN 127.0.0.1” and “You” tagged **Known Grok Bot** (`hb-r7-03-security-panel.png`). `classifySource` / `observeDevice` reclassifies by presence when `kind === 'ai'`.

### Residual notes (not filed as HB-R7-xx)

- **Low:** `POST /api/logout` clears cookies but does not revoke the session JWT server-side. A captured cookie value still authenticates until expiry.
- **Low:** The dedicated brute-force burst alert is skipped when the fifth human failure is recorded as `lockout`.
- **Low:** No distinct UI copy for HTTP 423 (`pin_locked`).

## Retest of former open items

These were called out as known open items on 1.20.0. On 1.20.1 they are **closed as Pass**:

- **Session token in `localStorage`:** leftover `homebase_jwt` / `homebase_jwt_exp` / `homebase_token` are cleared on first load (`migrateLegacyLocalSession()`). After login, no JWT is written back to `localStorage`. The browser session is the HttpOnly `hb_session` cookie. Reload stays signed in.
- **Token in the WebSocket URL:** the browser connects with a one-time `?ticket=` (TTL 30s, single use). A JWT in `?token=` is rejected (close 4401). Reuse and expiry of a ticket are also rejected. Playwright captured live `?ticket=` URLs and no `?token=`.

## Not tested, and why

- **True live HB-R3-01** (invalid model through a real Cursor agent) — this box has no Cursor API key; none was invented. Closest paths are documented in item 7.
- **True MCP-finished webhook delivery** — a job cannot start on the throwaway instance without a Cursor key, so the wire check used stubbed Cursor deps + a real local HTTP listener.
- **HTTPS via a real TLS terminator** — Secure cookie flags were verified with a trusted `X-Forwarded-Proto: https` header, not a TLS listener.
- **Simulated 500 and “network down” banners** in the PIN / login UI — not cleanly finished in Playwright. 401 and 429 were.
- **Security panel while a human lockout is actively counting down** — the PIN overlay blocks Settings during that window; time left was confirmed on the PIN pad instead. The panel was reviewed in the unlocked state (0/5 failures).
- **Creating a GitHub repo / signing in with `gh auth login`** — out of scope; Git & GitHub Settings and the Git tab were opened only.
- **`--deploy` / rollback on this machine** — not run, as requested.
- **The live :8090 GUI** — on purpose. That process was left running (pid 1198759). Live health may read `VERSION` from disk after a checkout; that is not proof the long-lived process has 1.20.1 logic in memory.
